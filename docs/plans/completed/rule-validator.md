# 업무 규칙 검증기 구현 계획

> 상태: 완료. 현재 `RULE.md` 기반 기본 정책을 사용하며, 사용자 설정으로 덮어쓰는 기능은 이후 `config` 단계에서 추가한다.

## 이 문서의 목적

다음 기능은 사용자가 작성한 에픽·스토리·작업 입력이 `RULE.md`의 업무 작성 규칙을 지키는지 검사하는 기능이다.

지금까지 만든 JSON 스키마는 “필수 값이 있는가?”, “날짜가 올바른가?”처럼 **입력의 모양**을 검사한다. 이번 검증기는 한 단계 더 나아가 “제목이 우리 팀의 규칙에 맞는가?”, “작업에 맞는 레이블은 무엇인가?”처럼 **업무의 의미와 표기 규칙**을 검사한다.

예를 들어 아래 입력은 JSON 형식 자체는 맞지만, 담당 영역이 `Frontend`라서 업무 규칙에는 맞지 않는다.

```text
[AUTH-001 | Frontend] 회원가입 화면 구현
```

검증기는 이를 아래처럼 알려준다.

```text
title: 담당 영역은 FE, BE, AI, QA, INFRA 중 하나여야 합니다.
```

## 이번 구현의 범위

포함하는 것:

- 에픽·스토리·작업 제목 형식 검사
- 작업의 공식 업무 분류와 담당 영역 검사
- 에픽/스토리의 스토리 포인트 금지 검사
- 작업 설명의 완료 기준 검사
- 유형과 제목에서 기본 레이블을 계산
- 오류와 경고를 한 번에 모아 반환

이번에 하지 않는 것:

- Jira API 호출 또는 실제 이슈 생성
- Jira에 있는 스토리를 조회해 작업의 기능 ID가 일치하는지 검사
- 스프린트·담당자·우선순위 존재 여부 검사
  - 이 값들은 이미 `issue-input.schema.ts`가 구조적으로 검사한다.
- 브랜치 생성
- “작업이 정확히 0.5~2일인지” 같은 사람이 판단해야 하는 항목을 오류로 차단

## 검증 흐름

```text
JSON 파일
  │
  ├─ 1. issue-input.schema.ts
  │      필수 항목, 날짜, 1·2·3·5·8 포인트 검사
  │
  └─ 2. issue-validator.ts   ← 이번 구현
         제목 규칙, 업무 분류, 레이블, 설명 품질 검사
            │
            └─ 오류/경고/계산된 레이블 반환
```

두 단계로 나누면 오류 메시지가 명확해진다. 예를 들어 `storyPoints: 13`은 1단계에서 바로 거절하고, `[AUTH-01]`처럼 세 자릿수가 아닌 기능 ID는 2단계에서 제목 규칙 오류로 알려준다.

## 만들 파일과 역할

```text
src/domain/
├─ policy/
│  └─ work-policy.ts             # 이미 존재: 영역·분류·스토리 포인트의 기준값
├─ input/
│  ├─ issue-input.types.ts       # 이미 존재: 입력 데이터 타입
│  └─ issue-input.schema.ts      # 이미 존재: JSON 구조 검사
└─ validation/
   ├─ validation-result.ts       # 오류·경고·계산 결과 타입
   ├─ title-parser.ts            # 제목에서 기능 ID, 분류, 담당 영역을 읽는 작은 함수
   └─ issue-validator.ts         # 이슈 유형별 규칙을 모아 검사하는 진입점

tests/domain/validation/
├─ title-parser.test.ts
└─ issue-validator.test.ts
```

### `title-parser.ts`가 필요한 이유

정규식을 검증기 곳곳에 직접 쓰면 수정할 때 누락하기 쉽다. 제목 해석을 한 파일에 모으면 다음처럼 다른 기능에서도 재사용할 수 있다.

```ts
parseTaskTitle("[AUTH-001 | FE] 이메일 회원가입 화면 구현")
// { kind: "feature", featureId: "AUTH-001", area: "FE", summary: "이메일 회원가입 화면 구현" }
```

나중에 Jira 레이블을 만들거나 브랜치 이름을 보완할 때도 같은 해석 결과를 사용할 수 있다.

## 규칙을 코드로 옮기는 기준

| 대상 | 검사할 규칙 | 결과 |
| --- | --- | --- |
| 에픽 | 기능 에픽은 `[도메인 코드] 이름` 형식 | 형식이 다르면 오류 |
| 에픽 | 지원 에픽의 명사형 여부 | 자동 판별이 어려워 경고 또는 통과 |
| 스토리 | `[기능코드-세자리번호] 기능명` 형식 | 다르면 오류 |
| 스토리 | 기본 레이블 | 항상 `feat` 계산 |
| 기능 작업 | `[기능ID | FE/BE/AI/QA/INFRA] 작업명` 형식 | 다르면 오류 |
| 공통 작업 | `[PLAN] 작업명` 또는 `[PLAN | FE] 작업명` 형식 | 분류·영역이 목록에 없으면 오류 |
| 작업 | 제목의 담당 영역에 맞는 기본 레이블 | `FE`, `BE`, `AI`, `Infra`, `Docs`, `기획` 중 하나 계산 |
| 작업 | 설명과 결과물 | 비어 있으면 오류; 결과물 문구가 지나치게 짧으면 경고 |
| 포인트 | 1·2·3·5·8만 허용, 8 초과 작업은 분리 | 입력 스키마가 오류로 차단 |

`INFRA`라는 담당 영역은 Jira 레이블에서는 `Infra`로 변환한다. `PLAN`, `UX`, `DESIGN` 작업은 `기획` 레이블을 사용한다. 이 변환 규칙도 정책 파일에 한곳으로 모은다.

## 검증 결과의 모양

검증기는 첫 오류에서 멈추지 않는다. 사용자가 한 번에 고칠 수 있도록 모든 문제를 배열로 돌려준다.

```ts
type ValidationMessage = {
  path: string;          // 예: "title", "description.deliverables"
  message: string;       // 사람이 읽는 수정 안내
};

type ValidationResult = {
  errors: ValidationMessage[];
  warnings: ValidationMessage[];
  derived: { labels: string[] };
};
```

CLI 명령은 나중에 이 결과를 아래처럼 출력한다.

```text
검증 실패 (2개)
- title: 기능 ID는 AUTH-001처럼 세 자리 번호를 사용해야 합니다.
- description.deliverables: 결과물을 하나 이상 입력해야 합니다.
```

## 구현 순서

1. `validation-result.ts`에 오류·경고·계산 결과 타입을 만든다.
2. `title-parser.ts`에 에픽·스토리·기능 작업·공통 작업 제목을 읽는 함수를 만든다.
3. 각 제목 형식의 정상·오류·경계값 테스트를 작성한다.
4. `issue-validator.ts`에서 이슈 유형에 따라 제목 검사와 레이블 계산을 조합한다.
5. 스토리, 기능 작업, 공통 작업의 정상 사례와 잘못된 영역·분류·세 자리 번호·설명 사례를 테스트한다.
6. `npm test`, `npm run typecheck`, `npm run build`가 모두 통과한 뒤에만 완료한다.

## 완료 기준

- `[AUTH-001] 이메일 회원가입` 스토리에서 `feat` 레이블이 계산된다.
- `[AUTH-001 | FE] 이메일 회원가입 화면 구현` 작업에서 `FE` 레이블이 계산된다.
- `[INFRA | BE] CI/CD 파이프라인 구축` 작업에서 `BE` 레이블이 계산된다.
- `[AUTH-01 | FE] ...`, `[AUTH-001 | Frontend] ...`, `[UNKNOWN] ...` 같은 제목은 이유를 포함해 거부된다.
- 한 입력에 오류가 여러 개면 모두 반환한다.
- 테스트에 정상 흐름과 엣지 케이스가 모두 포함되고 전체 테스트가 통과한다.

## 다음 단계와의 연결

이번 검증기는 외부 서비스에 의존하지 않는 순수 함수다. 이후 `validate` CLI 명령을 만들 때 이 함수를 호출하면 되고, Jira 생성 기능도 생성 직전에 같은 함수를 호출하면 된다. 그래서 명령어마다 규칙이 달라지는 문제를 막을 수 있다.
